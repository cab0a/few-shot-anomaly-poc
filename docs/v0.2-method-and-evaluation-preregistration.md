## English Summary

This document preregisters the first v0.2 method-and-evaluation study before the untouched VisA `pcb2` boundary is prepared. It fixes three methods, one shared 20-image normal reference set, normal-only threshold calibration, an opaque label-free final-test process, CPU timing, image-level metrics, mechanical failure selection, ordered hard gates, and the final decision rule. This milestone accesses no VisA archive, split row, label, image, score, or metric.

## Hypothetical Decision Question

For a hypothetical visual-inspection feasibility study with no more than 20 normal references, no anomalous training labels, and a general CPU, does any fixed candidate satisfy all operating-point and reproducibility gates on one untouched `pcb2` evaluation boundary?

The primary new-method question is whether the fixed `224 x 224` DINOv2 patch-nearest-neighbor candidate passes those gates. The two classical methods are full same-boundary comparators, not historical numbers copied from `pcb1`.

In this document, `ADOPT` means advance one method to the next controlled validation. It does not mean production deployment, customer acceptance, safety certification, or generalization beyond this public case study.

## Fixed Partitions

The official one-class split defines the train/test boundary.

### Normal reference partition

Select exactly 20 official `pcb2` normal training paths using this version-independent rule:

1. Normalize each eligible relative path to canonical POSIX form.
2. Create the UTF-8 string `few-shot-anomaly-poc:v0.2:pcb2:42:<relative-path>`.
3. Calculate SHA-256.
4. Sort by digest ascending and then relative path ascending.
5. Select the first 20 paths.

The fixed seed is `42`, the selection procedure is `sha256-path-ranking-v1`, and the namespace is `few-shot-anomaly-poc:v0.2:pcb2`. No image content or score may influence selection.

### Normal calibration partition

Every remaining official `pcb2` normal training path forms the calibration partition. Calibration may set one threshold per successfully fitted method and may do nothing else.

### Final-test partition

Every official `pcb2` test record forms the final-test partition. No record may be excluded for class, file size, visual content, expected difficulty, decode result, score, latency, or method failure.

The implementation must reject duplicate paths and require zero path overlap among reference, calibration, and final-test partitions. Counts must be derived only after exact archive and split verification; this document does not assume or publish an unverified `pcb2` count.

## Opaque Final-Test Boundary

Boundary preparation must use the committed `v0.2-opaque-scoring-manifest-v1` and `v0.2-sealed-label-mapping-v1` contracts.

1. A trusted preparation process parses the fixed official split without displaying class rows or class counts to the scorer.
2. Generate a new 32-byte ordering key with the operating system cryptographic random source.
3. Sort every final-test source path by `HMAC-SHA-256(key, source_path)` with source path as a deterministic collision tie-break.
4. Assign `asset-000000`, `asset-000001`, and subsequent sequential IDs.
5. Copy each encoded image to ignored staging as `assets/<opaque-id>.<extension>`.
6. Verify the staged byte count and SHA-256 against the source file.
7. Give the scorer only a manifest whose records contain exactly `asset_id`, `relative_path`, `byte_count`, and `sha256`.
8. Store `asset_id`, source path, and class label in a separate sealed mapping outside the scorer root.
9. Store the ordering key separately from both manifests; never expose it to a scoring process or public artifact.
10. Refuse any existing output path instead of overwriting it.

Before scoring, commit and push only the controlling preregistration identity, archive and split identities, total partition counts without final-test class counts, scoring-manifest SHA-256, sealed-manifest SHA-256, reference/calibration manifest identities, and boundary code identity.

The scorer must not receive the official split file, source-semantic paths, final-test class labels, class counts, the sealed mapping, or the HMAC key. No person or process used for method implementation, calibration, or scoring may manually inspect final-test image content before the reveal boundary.

## Fixed Methods

Exactly three methods enter the confirmatory comparison.

| Method ID | Role | Fitting data | Image score |
| --- | --- | --- | --- |
| `ecc_residual` | Interpretable classical baseline | Shared 20 normal references | Mean largest 1% aligned grayscale residual |
| `patch_hog_ocsvm` | Classical learned comparator | Shared 20 normal references | Mean 12 highest position-wise negative OCSVM margins |
| `dinov2_vits14_224_nn` | New representation candidate | Shared 20 normal references | Mean two largest exact nearest-neighbor cosine patch distances |

No method may receive an anomaly training label, calibration class other than known-normal status, final-test label, another method's score, or a result-derived parameter.

### Frozen classical comparators

`ecc_residual` and `patch_hog_ocsvm` must use the exact v0.1 preprocessing, fitting, scoring, failure, and fixed-threshold behavior without a `pcb2`-specific method adjustment. The frozen method values are identified by:

- [`configs/v0.1.yaml`](../configs/v0.1.yaml), SHA-256 `9a8149c0d37f86a4474089ae251bd4954071d7171f7110073e82c9796b52d917`;
- [v0.1 method specification](method-specification.md), SHA-256 `7c0259a8c5751c5bfd888c81258ed8dcb29154fc74ba1c16fb7545d6f0341c8c`.

The v0.1 configuration's `dataset`, `selection`, and `paths` values are not reused; the `pcb2` identities and partition rules in this document replace them. Its method, preprocessing, calibration, latency, failure-selection, and hard-gate values remain unchanged unless this document explicitly defines a stricter v0.2 process boundary.

This retains direct `512 x 512` grayscale preprocessing, the fixed ECC template and residual settings, the fixed Patch HOG grid, position-wise `StandardScaler`, position-wise RBF One-Class SVM, and their existing finite failure scores. The methods are refitted from the new shared `pcb2` reference set; no fitted `pcb1` state is reused.

ECC retains its preregistered rule that at least 16 of the 20 references, including the anchor, must fit successfully. Patch HOG requires all 20 complete reference feature matrices. A method-level fit failure is a result and cannot be rescued by replacing a reference.

| Field | Fixed value |
| --- | --- |
| Method ID | `dinov2_vits14_224_nn` |
| Source revision | `7764ea0f912e53c92e82eb78a2a1631e92725fc8` |
| Source archive SHA-256 | `c27dcdaf50e9fb5bbdf2bb529da357716372e19c6afab17d5350f3f0094aed4b` |
| Checkpoint SHA-256 | `b938bf1bc15cd2ec0feacfe3a1bb553fe8ea9ca46a7e1d8d00217f29aef60cd9` |
| Environment lock SHA-256 | `28a0878f3425bf6ea6fcc1631b168d67e6ddcc747d71f9c92c85b3aa9c706ec8` |
| Resolution | `224 x 224` only |
| Device and dtype | CPU, float32 |
| Fine-tuning | None |
| Reference count | Exactly 20 |
| Patch tokens per image | 256 |
| Memory-bank patches | 5,120 |
| Distance | Exact cosine distance, clamped to `[0, 2]` |
| Search block size | 2,048 reference patches |
| Aggregation | Arithmetic mean of the largest two query-patch distances |
| Finite image-level failure score | `2.0` with `score_status=failed` |

The candidate uses the already committed fixed scoring source, [`dinov2_scoring.py`](../src/few_shot_anomaly_poc/dinov2_scoring.py), with SHA-256 `944dc4c349aa011157ecc2e147bbcdd27da8b8c1fa1084fc0ae0e4641cec4cee`.

Each encoded source image is decoded by OpenCV `4.13.0.92` with `IMREAD_COLOR | IMREAD_IGNORE_ORIENTATION`. A fixed adapter validates a non-empty three-channel `uint8` BGR array, converts BGR to RGB, resizes directly to `512 x 512` with area interpolation, and returns a C-contiguous RGB `uint8` array. It applies no crop, aspect-ratio preservation, orientation transform, histogram operation, denoising, augmentation, mask, or content-dependent branch.

The isolated DINOv2 worker then applies the preflight-fixed RGB scaling, bicubic antialiased resize to `224 x 224`, ImageNet normalization, final-layer patch extraction, L2 normalization, exact blocked nearest-neighbor distance, and top-two aggregation.

All 20 reference feature matrices are concatenated in canonical POSIX relative-path ascending order. Any adapter, feature, concatenation, memory-bank, distance, or score failure makes DINOv2 fitting or that image score fail without retry, reference replacement, alternate resolution, or parameter fallback.

The following remain prohibited: `448`, register tokens, another backbone, PCA, masking, rotation augmentation, test-time augmentation, patch subsampling, FAISS, approximate search, quantization, compilation, batching, half precision, fine-tuning, and GPU execution.

## Fitting and Normal-Only Calibration

Apply these steps independently to each method:

1. Fit once from the same 20 normal reference IDs.
2. Record fitted-state identity, reference identities, successful and failed fitting records, and method status.
3. If the method fit succeeds, score every normal calibration image once.
4. Retain every scoring failure using the method's fixed finite failure score and failed status.
5. Sort scores by anomaly score ascending and then canonical POSIX relative path ascending.
6. Set `rank = ceil(0.95 * n)` for `n` calibration records.
7. Set the threshold to the score at `rank - 1`.
8. Classify an image as anomalous when its score status is failed or its score is strictly greater than the threshold.

Each method receives its own threshold. Calibration scores may not select a method, alter a feature, replace a reference, change a failure policy, set a score normalization, or choose a resolution. No anomaly image or final-test image may enter fitting or threshold calibration.

The fit and calibration artifacts, fitted-state hashes, thresholds, calibration counts, and realized normal calibration FPR must be committed and pushed before final-test scoring begins. Fitted binary state remains outside Git.

## Label-Free Final-Test Scoring

All three methods use the same opaque final-test asset-ID sequence. A method-level fit failure is recorded as `FIT_FAILED`; it receives `REJECT`, produces no fabricated per-image scores, and does not stop valid methods from completing.

For each successfully fitted method:

1. Load only the opaque scoring manifest, fixed method configuration, fixed fitted state, and method-specific threshold.
2. Process asset IDs in ascending sequential order.
3. Perform one full warm-up pass, followed by three full timed passes.
4. Use the first timed pass as the canonical label-free score and classification record.
5. Record every timed duration, score, score status, and failure code from all three passes.
6. Do not retry, discard, replace, or classify an observation as an outlier.
7. Require later-pass score status and failure code to match the canonical pass and successful scores to differ by no more than `1e-6` absolute.
8. Preserve exceptions, process termination, missing observations, and non-finite values as failures.

No score distribution, high-score image, threshold margin, class count, or cross-method difference may be manually inspected before every method has completed and the complete label-free bundle has been schema-validated, hashed, committed, and pushed.

Automated validation before that commit may check only schema, finite-number rules, fixed score ranges, asset-ID coverage and order, threshold provenance, record counts, byte identities, and hashes. It may not calculate a metric requiring a final-test class.

## CPU Measurement

The gating machine remains the recorded Intel Core i7-3630QM CPU under the fixed WSL2 boundary. CPU model, cores, RAM diagnostics, operating system, Python and dependency versions, thread settings, affinity, and concurrent benchmark check must be recorded.

The per-image boundary excludes file I/O, encoded-image decoding, model loading, fitted-state loading, one-time reference fitting, calibration, artifact writing, and label reveal. It includes every deterministic method operation after the decoded array exists and before one scalar image score is materialized.

- For ECC and Patch HOG, retain the v0.1 decoded-grayscale-`uint8`-to-score boundary, including their fixed `512 x 512` preprocessing.
- For DINOv2, measure the decoded-BGR-`uint8` adapter and the isolated `512 x 512` RGB-to-score worker. The per-invocation DINOv2 duration is the checked sum of matching adapter and worker nanoseconds for the same pass and asset ID. Inter-process file transfer is excluded and must be reported as an orchestration limitation.

Use `time.perf_counter_ns`, one full-sequence warm-up pass, three timed passes, median with the arithmetic mean of the middle pair when even, and nearest-rank p95 over all expected timed invocations. Failed-score timings remain included when a duration exists. A crash, missing timing, timer error, or incomplete invocation set fails the latency gate.

The earlier synthetic DINOv2 p95 of `0.679490250 s/image` is preflight eligibility evidence only. It is not reused as the final `pcb2` latency gate. A DINOv2 p95 above one second in this fixed label-free run causes its latency gate to fail without optimization or fallback.

## Offline Score Reproduction

After label-free scoring is committed and before labels are revealed, start a fresh offline process for each successfully scored method and regenerate the canonical scores for the first 10 opaque asset IDs.

The check passes only when:

- code, configuration, environment lock, model asset, fitted-state, input-array, scoring-manifest, and threshold identities match;
- no network access is required;
- asset IDs and order match;
- score status and failure code match exactly;
- all successful scores are finite and within their fixed method range; and
- maximum absolute score difference is `<= 1e-6`.

A failed reproduction is retained, makes that method's reproducibility gate fail, and does not authorize a new scoring run.

## Label Reveal

Labels may enter only after all available methods' immutable label-free scoring and reproduction artifacts are committed and pushed.

The reveal process must:

1. Verify the committed scoring-manifest and sealed-mapping SHA-256 values.
2. Reject missing, extra, duplicate, or out-of-order opaque asset IDs.
3. Join each method's canonical score and classification to exactly one sealed label by opaque asset ID.
4. Require only `normal` or `anomaly` as the image-level class.
5. Preserve every score, status, failure code, threshold, and prediction without replacement.
6. Write a new reveal artifact without modifying the label-free bundle.
7. Publish source-path and label mapping evidence only after reveal; do not publish raw VisA bytes.

No threshold, score, method, prediction, or failure rule may cross from the reveal side back into scoring.

## Primary Metrics

Anomaly is the positive class. Calculate each metric independently for every successfully scored method from the complete revealed final-test set.

| Metric | Role |
| --- | --- |
| Image-level AUROC | Descriptive ranking metric; not a gate |
| Image-level AUPRC | Descriptive ranking metric; report with class support; not a gate |
| Fixed-threshold normal FPR | Primary operating-point gate |
| Fixed-threshold anomaly recall | Primary operating-point gate |
| True positive, false negative, true negative, and false positive counts | Required decision evidence |
| Image-score failure count | Required operational evidence |
| CPU median latency | Descriptive latency evidence and selection tie-break |
| CPU p95 latency | Primary latency gate |

Every final-test record remains in the denominators and ranking metrics. A failed image score retains its finite method-specific failure score and is operationally predicted anomalous. AUROC or AUPRC cannot waive an operating-point failure.

No confidence interval, significance test, pooled `pcb1`/`pcb2` estimate, or pixel-level metric is part of the primary result.

## Mechanical Failure-Case Selection

After label reveal, select up to five cases per error type and method:

- false positives: anomaly score descending, then opaque asset ID ascending;
- false negatives: anomaly score ascending, then opaque asset ID ascending.

Selection code receives no image pixels. It records asset ID, revealed source path, true class, prediction, score, threshold, signed margin, score status, failure code, and deterministic rank.

After metrics, gate outcomes, and selected-case identities are committed, a local review may open only those mechanically selected images. The review must not change a score, threshold, metric, gate, selected identity, or method. It may assign exactly one disposition per otherwise gate-passing method:

- `no_material_boundary`: no selected case establishes a material restriction on the hypothetical intended use;
- `guardrail_required`: a selected case supports one explicit observable input restriction or manual-review guardrail;
- `intended_use_contradicted`: selected cases contradict the stated use and no bounded guardrail is defensible.

Observations must distinguish visible facts from inferred causes. No unselected final-test image may be opened for exploratory error analysis in the confirmatory v0.2 run.

VisA image pixels or crops are not committed by default. If the user later separately authorizes a public image, it requires VisA attribution, the Zou et al. citation, the Amazon copyright notice, a link to the official source and CC BY 4.0, and a description of every crop, resize, overlay, or annotation.

## Acceptance Gates

Apply these gates independently to each method in this exact order:

| Order | Gate | Pass condition |
| ---: | --- | --- |
| 1 | Method fit | Complete fixed fitted state |
| 2 | Test leakage | None detected |
| 3 | Final-test normal FPR | `<= 0.05` at the normal-only threshold |
| 4 | Final-test anomaly recall | `>= 0.90` at the same threshold |
| 5 | CPU p95 scoring latency | `<= 1.0 s/image` at the fixed boundary |
| 6 | Normal reference budget | Exactly 20 images and no replacement |
| 7 | Anomaly training labels | None used |
| 8 | Reproducibility | Fixed first-10 offline check passes |

These are hypothetical public case-study gates, not customer requirements or general recommendations. No weighted aggregate, hard-gate waiver, AUROC, AUPRC, published benchmark, visual impression, median latency, or another method's result may override a failed gate.

## Per-Method Decision

Apply hard gates before the selected-case review.

- `ADOPT`: every hard gate passes and the fixed review disposition is `no_material_boundary`.
- `ADOPT WITH CONDITIONS`: every hard gate passes and the disposition is `guardrail_required`; the exact condition must be recorded.
- `REJECT`: any hard gate fails, test leakage is detected, required evidence is incomplete, or the disposition is `intended_use_contradicted`.

`ADOPT WITH CONDITIONS` cannot rescue a failed numerical, process, fitting, or reproducibility gate.

## Project Recommendation

Report every per-method decision, including the DINOv2 decision, before selecting one project recommendation.

If every method is `REJECT`, the project decision is `REJECT`. Otherwise, select among non-rejected methods using this fixed lexicographic order:

1. `ADOPT` before `ADOPT WITH CONDITIONS`;
2. higher fixed-threshold anomaly recall;
3. lower fixed-threshold normal FPR;
4. lower CPU p95 latency;
5. lower CPU median latency; and
6. `ecc_residual`, then `patch_hog_ocsvm`, then `dinov2_vits14_224_nn` if every preceding value is exactly equal, reflecting increasing model and dependency complexity.

The project decision equals the selected method's decision. AUROC and AUPRC remain descriptive. A selected method is only recommended for the next controlled validation under the recorded hypothetical conditions.

## Ordered Stop Conditions

Apply these conditions before or during the indicated stage. A later success cannot waive an earlier failure.

1. Stop if the controlling preregistration commit or document SHA-256 is unavailable or changed.
2. Stop before split parsing if the archive or official split identity differs.
3. Stop before image decoding if the normal partitions and opaque boundary cannot be created without overlap, overwrite, or scorer-visible labels.
4. Stop before fitting if source, model, environment, configuration, or license identities differ from the fixed records.
5. Stop before final scoring if the freeze, reference fit, normal calibration, thresholds, or fitted-state identities are incomplete.
6. Stop before reveal if any available method's expected label-free artifact is missing, mutable, uncommitted, or unpushed.
7. Stop before reveal if the fresh offline reproduction check is incomplete or if the scorer accessed labels, semantic paths, the official split, or the sealed mapping.
8. Stop evaluation if reveal input has a missing, extra, duplicate, or out-of-order asset ID.
9. Stop decision generation if metrics, latency, failures, process evidence, or gate inputs are incomplete.
10. Return and preserve `REJECT` when the ordered decision rule requires it; do not revise a gate or method afterward.

A method-level fit or score failure is method evidence rather than permission to change the method. Other fixed methods may continue when the shared dataset and boundary remain valid.

## Change Control

Before real boundary preparation begins, a factual correction requires a new commit and a new preregistration ID if it changes any method, input, partition, threshold, metric, timing boundary, tolerance, gate, or decision rule.

After boundary preparation begins, this document must not be edited in place. If an implementation defect is discovered before any final-test score is materialized, preserve the stopped attempt and create a new preregistration before retrying.

After any final-test score is materialized, no result-responsive change or ordinary rerun is allowed. A confirmed implementation defect requires preserving the invalid attempt, keeping labels sealed, writing a new preregistration that identifies only the defect correction, and obtaining an explicit new authorization before another score run. After labels are revealed, no confirmatory rerun is allowed under this preregistration ID.

Bad results, fit failures, scoring failures, latency failures, reproduction failures, boundary stops, and `REJECT` decisions remain publishable evidence.
