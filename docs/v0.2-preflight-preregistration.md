# v0.2 Preflight Preregistration

本書は、DINOv2 patch nearest neighborを実評価へ進める前に、CPU実行可能性だけを検証するv0.2 preflightを固定した事前登録です。標準DINOv2 ViT-S/14、224/448解像度、分離したCPU-only依存環境、公式モデル資産の検証手順、合成入力による処理時間計測、停止条件を定義しています。

## English Summary

This document preregisters a label-free CPU feasibility spike for the proposed DINOv2 ViT-S/14 patch-nearest-neighbor method. It fixes the model identity, isolated dependency target, official-asset verification procedure, deterministic synthetic workload, `224 x 224` and `448 x 448` timing rules, ordered stop conditions, and the future untouched VisA `pcb2` evaluation boundary. It does not authorize model adoption, performance evaluation, or a change to the completed v0.1 decision.

## Objective

Determine whether one fixed DINOv2 patch-nearest-neighbor candidate can meet the existing hypothetical CPU p95 gate before any dataset performance study is authorized.

This preflight answers only:

1. Can the exact third-party source, checkpoint, environment, and license boundary be reproduced?
2. Can the complete decoded-RGB-to-image-score path run on the recorded CPU with p95 latency no greater than one second at either preregistered resolution?
3. Can scores be regenerated within the fixed numerical tolerance from the same assets and configuration?

It does not answer whether DINOv2 detects anomalies accurately.

## Fixed Candidate Scoring Path

The CPU workload must implement the following path and no other candidate:

1. Accept one contiguous `512 x 512 x 3` RGB `uint8` array that is already decoded in memory.
2. Convert to a float32 NCHW tensor in `[0, 1]`.
3. Resize to the selected square resolution with bicubic interpolation, `align_corners=False`, and antialiasing enabled.
4. Normalize channels with mean `(0.485, 0.456, 0.406)` and standard deviation `(0.229, 0.224, 0.225)`.
5. Extract the normalized final-layer patch tokens using `get_intermediate_layers` with one layer, no reshape, and no class-token return.
6. L2-normalize every 384-dimensional patch vector with epsilon `1e-12`.
7. Compare each query patch with the fixed normal memory bank by exact cosine distance `clamp(1 - dot_product, 0, 2)`.
8. Search the memory bank in deterministic blocks of 2,048 reference patches and retain the minimum distance for each query patch.
9. Sort patch distances descending and return the arithmetic mean of the largest `max(1, floor(0.01 * patch_count))` distances.

The final aggregation matches AnomalyDINO's published implementation concept of mean top-1-percent patch distance. At `224 x 224`, the score averages the largest 2 of 256 patch distances. At `448 x 448`, it averages the largest 10 of 1,024 patch distances.

No FAISS, approximate search, masking, rotation augmentation, test-time augmentation, patch subsampling, feature projection, quantization, compilation, half precision, pixel-level output, or GPU operation is permitted.

## Deterministic Synthetic Workload

The CPU preflight must not read VisA or any anomaly label.

For each resolution, use the same generated decoded-image workload:

| Item | Fixed value |
| --- | --- |
| Generator | `numpy.random.Generator(numpy.random.PCG64(42))` |
| Generation order | 20 reference arrays, then 100 query arrays |
| Array shape | `512 x 512 x 3` |
| Array dtype | `uint8` |
| Value generation | integers in `[0, 256)` |
| Reference IDs | `synthetic/reference/000` through `synthetic/reference/019` |
| Query IDs | `synthetic/query/000` through `synthetic/query/099` |
| Storage during run | generated before timing and retained in memory |

The runner must record SHA-256 for each generated array before preprocessing. The same 20 arrays form a separate memory bank at each resolution. Memory-bank extraction, model loading, input generation, and hashing occur outside the per-image timed boundary.

The random arrays exist only to create a fixed dense CPU workload. They are not anomaly examples, evaluation data, or evidence about detection quality.

## CPU Measurement Rule

### Boundary

The timed boundary begins immediately before conversion of one decoded `512 x 512 x 3` RGB `uint8` array and ends after one finite scalar image score is materialized on the CPU.

It includes:

- RGB array-to-tensor conversion;
- float conversion and scaling;
- bicubic resize and antialiasing;
- channel normalization;
- DINOv2 forward feature extraction;
- patch L2 normalization;
- exact chunked nearest-neighbor distance; and
- top-1-percent image-score aggregation.

It excludes:

- file I/O and image decoding;
- random input generation and hashing;
- source or checkpoint download;
- model construction and checkpoint loading;
- reference feature extraction and memory-bank construction;
- process startup;
- artifact serialization; and
- final-test classification or metrics.

### Invocations

For each resolution:

1. Construct and validate the model and corresponding 20-image memory bank.
2. Run 25 unrecorded warm-up invocations using `synthetic/query/000`.
3. Run three timed passes over all 100 query IDs in ascending order.
4. Record all 300 durations with `time.perf_counter_ns`.
5. Record the scalar score and failure state for every invocation.

No invocation may be retried, discarded, replaced, or treated as an outlier.

### Summaries

- Median is the arithmetic mean of the two middle sorted observations because 300 is even.
- p95 is the nearest-rank value at rank `ceil(0.95 * 300) = 285` in ascending order.
- Durations are stored as integer nanoseconds and reported in seconds only as a derived value.
- Peak resident set size is recorded as a diagnostic, not an acceptance gate.
- A non-finite score, exception, process termination, out-of-memory event, or missing observation is a scoring failure.
- A resolution with any scoring failure does not receive a passing CPU decision, even if its finite-duration p95 is within one second.

### Resolution gate and selection

A resolution passes only when:

- all 300 timed invocations complete;
- all scores are finite;
- p95 latency is `<= 1.0 s/image`; and
- reproducibility checks pass.

The resolution is selected without anomaly-performance evidence:

| `224` | `448` | Preflight result |
| --- | --- | --- |
| pass | pass | Select `448`; `PROCEED` |
| fail | pass | Select `448`; `PROCEED` |
| pass | fail | Select `224`; `PROCEED` |
| fail | fail | `DO NOT PROCEED` |

The preference for `448` when both pass is preregistered because it retains four times as many patch locations. This is a spatial-resolution rationale, not an accuracy claim.

## Reproducibility Check

After the timing run, start another fresh offline process and regenerate the first 10 query scores for each passing resolution.

The check passes only if:

- source commit, source SHA-256, checkpoint SHA-256, environment lock SHA-256, configuration SHA-256, and generated input SHA-256 values match;
- no network access is required;
- all regenerated scores are finite;
- asset IDs and score order match; and
- maximum absolute score difference is `<= 1e-6`.

The second process is not included in the latency observations.

## Ordered Stop Conditions

Apply the following conditions in order. A later success cannot waive an earlier failure.

1. **Preregistration identity:** stop if this document's controlling commit cannot be identified or the worktree contains an unregistered change affecting the preflight.
2. **Source and license:** stop if the exact standard DINOv2 source revision, Apache-2.0 boundary, or non-register model identity cannot be verified.
3. **Dependency resolution:** stop if the exact CPU-only environment cannot be locked, if the expected CPU wheel is unavailable, or if resolving it requires a changed direct version or an unreviewed dependency.
4. **Checkpoint acquisition:** stop if the checkpoint transfer, observed identity, safe load, or strict architecture load fails.
5. **Third-party separation:** stop if required licenses and notices cannot be inventoried without applying PolyForm terms to third-party material.
6. **Target machine:** stop if the gating run is not performed on the fixed CPU boundary.
7. **Execution integrity:** stop if any unregistered GPU, quantization, compilation, batching, approximation, augmentation, masking, or dependency is used.
8. **CPU result:** stop with `DO NOT PROCEED` if neither resolution passes the fixed latency and failure gates.
9. **Reproducibility:** stop if offline score regeneration exceeds the fixed tolerance or requires a mutable network resource.
10. **Evaluation boundary:** do not begin VisA scoring if the opaque, untouched boundary described below cannot be established.

The stop decision is evidence. Thresholds, invocation counts, resolutions, thread settings, or the one-second gate must not be changed in response to a result.

### Opaque final-test preparation

Only after the CPU preflight returns `PROCEED`, a separate boundary-preparation step must:

1. Verify the archive and split identities above without decoding final-test content.
2. Select the 20 normal references by SHA-256 path ranking of `<namespace>:<seed>:<POSIX relative path>`.
3. Assign every official `pcb2` final-test record an opaque sequential asset ID using a secret HMAC-SHA-256 ordering key generated for the boundary.
4. Copy final-test files into an ignored staging directory named only by opaque asset ID and extension.
5. Write a label-free scoring manifest containing only opaque asset ID, opaque staged relative path, byte count, and file SHA-256.
6. Write the source-path and label mapping to a separately sealed local manifest that the scorer cannot read.
7. Commit only the split identity, partition counts, scoring-manifest SHA-256, sealed-manifest SHA-256, and boundary-generation code before scoring.
8. Prevent the scorer from receiving class-semantic source paths, the official split file, the HMAC key, or the label mapping.
9. Reveal and join labels only after all candidate methods have written immutable label-free scores and classifications.
10. Publish enough mapping evidence after final evaluation to reproduce the join without publishing raw VisA data.

This is a procedural and programmatic label boundary, not a claim that public VisA labels are unknowable. Any manual inspection of final-test content or semantic source paths before label reveal invalidates the confirmatory evaluation.

The classical v0.1 methods must be refit, normally calibrated, and scored on this same `pcb2` boundary if they are used as v0.2 comparators. Metrics from `pcb1` must not be directly compared as if they came from the same test population.

## Decision Rule

Return `PROCEED` only if:

- stop conditions 1 through 7 pass;
- at least one resolution passes the CPU gate;
- the offline reproducibility check passes for every passing resolution; and
- the untouched evaluation boundary remains feasible.

Otherwise return `DO NOT PROCEED`.

No weighted score, AUROC, published benchmark result, visual impression, or non-gating median latency can override a failed condition. `PROCEED` authorizes a separate v0.2 method-and-evaluation preregistration; it does not adopt DINOv2.
