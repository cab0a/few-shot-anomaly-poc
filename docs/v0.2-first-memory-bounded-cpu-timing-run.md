# v0.2 First Fixed Memory-Bounded CPU Timing Run

## 日本語概要

本書は、事前登録済みのDINOv2 CPU timing workloadを同じWSL2 CPU環境で初めて正式実行した記録です。固定合成reference 20件とquery 100件をmemory-mapped storeから一枚ずつ処理し、224と448を別processで順番に測定しました。

各解像度300件を欠測・scoring failure・OOMなく完了しました。224のp95は0.6795秒で1秒ゲートを通過し、448は3.6253秒で不通過でした。この結果により224だけをoffline score再現確認へ進めますが、VisA、label、threshold、異常検知精度には触れておらず、DINOv2の最終採否ではありません。詳細は以下の英語本文を参照してください。

## English Summary

The first formal memory-bounded DINOv2 CPU timing workload completed on the preregistered WSL2 CPU environment. Both fresh resolution processes produced all 300 required finite observations without a scoring failure, missing observation, or out-of-memory event. Resolution `224` passed the fixed one-second p95 gate at `0.679490250 s`; resolution `448` failed it at `3.625274025 s`. The protocol therefore selects only `224` for the separate offline score-reproduction check. This result is synthetic CPU timing evidence, not anomaly-detection performance or a DINOv2 adoption decision.

## Fixed Workload

The run used the workload and resource policy fixed before timing:

- standard non-register `dinov2_vits14` with the previously verified checkpoint;
- CPU-only float32 inference with 4 intra-op and 1 inter-op PyTorch threads;
- deterministic algorithms and no xFormers runtime;
- 20 synthetic normal references and 100 synthetic queries generated by PCG64 seed `42`;
- an ignored read-only NumPy memory map with one source image copied at a time;
- 25 untimed warm-up calls per resolution;
- three ordered passes over query IDs `000` through `099`;
- 300 timed invocations per resolution using `time.perf_counter_ns`;
- median and nearest-rank p95 with rank `285`; and
- a hard latency gate of p95 no greater than `1,000,000,000 ns`.

Resolution `224` completed before the fresh `448` process began. Input-store access, the memory-map copy, and per-image hash verification remained outside the decoded-RGB-to-scalar timing boundary.

The `448` worker returned the protocol's expected nonzero gate-failure exit code after writing a complete valid artifact. This was a latency failure, not a crash or incomplete run. The parent retained it and continued to a valid timing-stage decision.

## Memory Interpretation

The same constrained WSL2 environment was used without increasing its configured memory. The precondition record observed `4,045,004,800` bytes of total visible RAM and `3,058,700,288` bytes available before the run. Total visible RAM was diagnostic, as preregistered; it was not a gate.

The observed peak RSS values were well below total visible RAM, and neither process produced a Python memory error, framework out-of-memory error, operating-system termination, missing artifact, or incomplete observation set. Peak RSS remains descriptive rather than an acceptance gate.

## Resolution Selection

The preregistered selection table chooses the only passing resolution when exactly one resolution passes. Therefore:

- `224` advances to the separate offline score-reproduction condition;
- `448` does not advance under the fixed one-second p95 requirement; and
- no alternative score, weighted aggregate, or favorable median overrides the `448` p95 failure.

This selection is not `PROCEED` for v0.2 as a whole. The offline first-10-score reproduction condition and untouched evaluation boundary must still pass before the preflight can return `PROCEED`.

## Preserved Evaluation Boundary

The formal timing run:

- used synthetic inputs only;
- did not access VisA, `pcb1`, `pcb2`, or any image label;
- did not calibrate a threshold;
- did not calculate AUROC, AUPRC, FPR, recall, or another anomaly metric;
- did not fit from real normal images;
- did not select failure-case images; and
- did not adopt or reject DINOv2 for anomaly detection.

The recorded scalar scores only prove that the fixed scoring path returned finite outputs during timing. They must not be interpreted as defect scores with known accuracy.

## Limitations

- The workload contains deterministic synthetic noise rather than inspection images.
- The latency values apply to the recorded CPU, WSL2, software environment, thread settings, and scoring boundary.
- Only one formal timing run was performed; no variance across process launches or machines is claimed.
- Peak RSS is a process high-water mark, not an allocation trace or proof of a universal minimum-memory requirement.
- Passing `224` latency does not establish anomaly ranking, threshold transfer, defect recall, or production suitability.
- Failing `448` latency does not establish that the resolution is unusable under a different requirement or hardware budget.

## Next Milestone

The next milestone is **the first fixed offline score-reproduction run for resolution `224`**. It must start in a separate fresh process with network access disabled, regenerate the fixed inputs, load the same source and checkpoint identities, reproduce the first 10 timed-run scores within absolute tolerance `1e-6`, and preserve the result without accessing VisA or labels. No `448` reproduction is required because `448` failed the latency gate.
