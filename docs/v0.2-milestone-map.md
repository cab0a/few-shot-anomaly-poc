## English Summary

The fixed `v0.2` evaluation protocol is divided into nine public milestone labels from `v0.2.0` through `v0.2.8`. These labels communicate progress without renaming or invalidating preregistered documents, hashes, schema versions, artifact paths, or the final run ID.

## Purpose

The repository previously used `v0.2` for every DINOv2-related checkpoint. That was correct for protocol identity but too coarse for progress reporting. From this point forward:

- `v0.2` remains the immutable parent evaluation-protocol identity;
- `v0.2.x` identifies a bounded public milestone within that protocol;
- the labels are not package releases, API compatibility promises, or retrospective protocol changes; and
- historical filenames and artifact paths remain unchanged when their bytes or identities are already fixed.

## Fixed Milestone Sequence

| Label | Milestone | Completion boundary |
| --- | --- | --- |
| `v0.2.0` | DINOv2 CPU feasibility and preflight | CPU feasibility, dependency and model-asset checks, fixed scoring path, timing, offline reproduction, and final `PROCEED` preflight completed without VisA evaluation access |
| `v0.2.1` | Method preregistration and machine-readable contract | Three methods, partitions, metrics, timing, artifacts, hard gates, config, schema, and validators fixed before `pcb2` entry |
| `v0.2.2` | Boundary preparation | Exact archive and split verified; normal reference/calibration identities and opaque final-test boundary created without decoding or scoring |
| `v0.2.3` | Pre-evaluation freeze checkpoint | Source, config, schema, environment, partition, opaque-boundary, method-order, and gate-order identities fixed before fitting |
| `v0.2.4` | Reference fitting and normal-only calibration | All three fixed methods fitted or failed; thresholds fixed from normal calibration only |
| `v0.2.5` | Label-free final-test scoring and CPU latency | One canonical score pass and all fixed CPU timing observations committed without label access |
| `v0.2.6` | Offline reproduction and pre-reveal checkpoint | First-ten offline reproduction completed; all label-free evidence committed and pushed before reveal |
| `v0.2.7` | Label reveal, metrics, and failure cases | Exact opaque-ID join, image-level metrics, confusion counts, and mechanical FP/FN selection committed |
| `v0.2.8` | Hard-gate decision, public report, and completion review | Per-method and project decisions, limitations, next validation, manifest, README, and release audit completed |

## Current Position

`v0.2.5` is complete. The next authorized milestone is `v0.2.6 — Offline Reproduction and Pre-Reveal Checkpoint`.

The `v0.2.5` artifacts record 200 canonical scores, 200 fixed-threshold classifications, and 600 CPU observations per method without label, semantic-path, official-split, HMAC-key, or sealed-mapping access. The raw bundles, exact hashes, and committed validation tests were pushed before their label-free aggregates were manually inspected. No label reveal may begin until the fixed first-ten offline reproduction and complete pre-reveal checkpoint are committed and pushed. The scoring execution commit remains distinct from the v0.2.3 freeze commit and is explicitly retained for the reproducibility review.

## Identity Preservation

The milestone labels do not alter:

- preregistration ID `v0.2-pcb2-method-evaluation-1`;
- run ID `visa-pcb2-v0-2-final`;
- config path [`configs/v0.2.yaml`](../configs/v0.2.yaml) or its fixed SHA-256;
- artifact schema version `evaluation-artifacts/v0.2` or its fixed SHA-256;
- existing `docs/v0.2-*.md` filenames;
- existing `artifacts/v0.2/` locations;
- method identifiers, parameters, partitions, thresholds, metrics, timing rules, hard gates, or decision rules; or
- any committed historical document whose exact bytes are evidence.

The labels are documentation metadata. They do not authorize a later stage, waive a failed condition, or permit a rerun.

## Change Rule

New public records and status text should identify the relevant `v0.2.x` milestone. Machine-readable artifact fields continue to use the already frozen parent contract values unless the preregistered schema explicitly provides a milestone field.

If a future change modifies a fixed method, input, partition, metric, timing boundary, hard gate, or decision rule, it requires a new preregistration rather than another `v0.2.x` label.
