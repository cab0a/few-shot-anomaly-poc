## English Summary

The v0.2 preregistration is translated into an exact configuration, artifact schema, standard-library validator, and synthetic contract tests before any `pcb2` evaluation-boundary preparation. This milestone defines evidence shapes and rejection rules; it does not access VisA data, execute a model, create a final-test bundle, or provide performance evidence.

## Fixed Evaluation Configuration

The contract fixes these three method identifiers in order:

1. `ecc_residual`;
2. `patch_hog_ocsvm`, mapped to the existing implementation identifier `patch_hog_one_class_svm`; and
3. `dinov2_vits14_224_nn`.

All methods use the same 20 normal references selected by seed `42` and the fixed SHA-256 path-ranking rule. Remaining normal training images form the threshold-calibration partition. The official `pcb2` test set is reserved for one fixed label-free scoring pass followed by the controlled label reveal.

Thresholds use the nearest-rank 95th percentile of normal calibration scores. Classification is anomalous only when scoring fails or the score is strictly greater than the fixed threshold. Anomaly labels cannot enter fitting or calibration.

The final timing contract uses one untimed warm-up and three timed passes on CPU. The canonical score is taken from timed pass zero. DINOv2 latency includes both the fixed input adapter and scorer; classical-method latency is the scorer duration. The first ten opaque assets must reproduce offline within an absolute score tolerance of `1e-6` before reveal.

## Artifact Contracts

The schema defines exact JSON and CSV fields, nullability, enums, primary keys, sort keys, and stage boundaries.

| Contract | Format | Boundary or purpose |
| --- | --- | --- |
| `boundary_record` | JSON | Partition counts and sealed opaque-boundary identities |
| `pre_evaluation_freeze` | JSON | Source, configuration, schema, partition, method, and gate identities before evaluation |
| `fit` | JSON | Per-method reference fitting outcome and external fitted-state identity |
| `calibration_score` | CSV | Normal-only calibration scores |
| `calibration_summary` | JSON | Fixed threshold, rank, failures, and realized calibration FPR |
| `score` | CSV | Label-free canonical final-test scores |
| `classification` | CSV | Label-free fixed-threshold classifications |
| `latency_observation` | CSV | Three timed observations per opaque asset |
| `reproduction` | CSV | Offline first-ten score comparison |
| `pre_reveal_checkpoint` | JSON | Committed and pushed label-free evidence identity |
| `label_reveal` | CSV | Opaque asset-to-path and true-class join after the checkpoint |
| `metrics` | JSON | Ranking metrics, confusion counts, fixed-threshold rates, and failures |
| `failure_case` | CSV | Mechanically ranked false positives and false negatives |
| `method_decision` | JSON | Ordered hard-gate trace and per-method decision |
| `project_decision` | JSON | Fixed lexicographic method selection or project rejection |
| `bundle_manifest` | JSON | Sorted artifact identities without self-hashing |

All records use relative POSIX paths, finite numbers, fixed UTF-8 serialization, deterministic ordering, and non-overwriting destinations. Raw dataset content, decoded arrays, fitted binary state, checkpoint bytes, DINOv2 source bytes, HMAC keys, and the sealed pre-reveal mapping remain outside public artifacts.

## Label-Reveal Boundary

The final-test `score`, `classification`, `latency_observation`, and `reproduction` contracts are label-free. Their schemas exclude:

- `true_class`;
- `class_label`;
- `source_path`;
- `official_split`;
- `sealed_mapping`; and
- `hmac_key`.

The label-free checkpoint must identify a Git commit containing the complete score-side evidence and confirm that the commit was pushed before labels are accessed. The later `label_reveal` contract contains no anomaly score or prediction field. Scores and labels are joined by exact opaque asset ID only after that checkpoint.

## Score and Failure Rules

Each method has a fixed successful-score range and a fixed finite failure score:

| Method | Successful score range | Fixed failure score |
| --- | --- | ---: |
| `ecc_residual` | `[0, 1]` | `1.0` |
| `patch_hog_ocsvm` | `(-1e12, 1e12)` | `1e12` |
| `dinov2_vits14_224_nn` | `[0, 2]` | `2.0` |

A successful record must have no failure code and a score inside its method range. A failed record must have a non-empty failure code and the exact fixed failure score. This prevents failures from silently appearing normal and avoids non-finite JSON values.

## Metrics and Decision Rules

Image-level AUROC and AUPRC remain descriptive. Normal FPR, anomaly recall, and CPU p95 latency are hard-gate inputs. Confusion counts, score-failure counts, CPU median latency, and mechanically selected errors are required evidence.

The validator preserves this hard-gate order:

1. method fit;
2. test leakage;
3. final-test normal FPR `<= 0.05`;
4. final-test anomaly recall `>= 0.90`;
5. CPU p95 scoring latency `<= 1.0 s/image`;
6. exactly 20 normal references;
7. no anomalous training labels; and
8. successful fixed first-ten reproduction.

After the first failed gate, every later gate must be `not_evaluated`. Weighted scores and hard-gate waivers are fixed to false. `ADOPT WITH CONDITIONS` is allowed only when every gate passes and the fixed failure review identifies a necessary guardrail; it cannot rescue a failed gate.

## Validation Evidence

The validator uses only Python's standard library. The focused tests use generated dictionaries and do not read an image or run any anomaly method.

```bash
uv run --locked --no-sync ruff check \
  src/few_shot_anomaly_poc/v0_2_evaluation_contract.py \
  tests/test_v0_2_evaluation_contract.py
uv run --locked --no-sync pytest -q tests/test_v0_2_evaluation_contract.py
```

The tests cover exact identities, protected label fields, method-specific score ranges, fixed failure scores, strict threshold behavior, CPU timing boundaries, three-pass completeness, first-ten reproduction rules, opaque asset ordering, fit and calibration counts, metric arithmetic, ordered decisions, and manifest self-exclusion.

## Stage Boundary

This milestone did not:

- acquire or inspect a VisA archive or official split;
- enumerate a `pcb2` path;
- create references, calibration IDs, opaque final-test IDs, or a sealed mapping;
- decode an image;
- load or execute DINOv2 or a classical method;
- fit a method or calibrate a threshold;
- create a final-test score, latency value, metric, failure selection, or decision; or
- create an evaluation artifact directory.

The next authorized stage is `boundary_preparation`. It must verify the fixed external archive and split identities before parsing, create non-overlapping normal partitions and an opaque label-free scoring manifest, keep the key and sealed mapping outside Git, and stop before method fitting or final-test scoring.

## Known Limitations

- The custom schema is a repository contract, not JSON Schema and not a general-purpose interchange standard.
- Contract tests prove rejection behavior for synthetic records; they do not prove method correctness or `pcb2` performance.
- The machine-readable files do not make the evaluation double-blind on their own. The later boundary implementation must enforce the sealed mapping and scorer-visible field restrictions.
- Exact config and schema hashes require an explicit new preregistration when a factual correction changes a fixed evaluation rule.
- No production, deployment, cross-category, pixel-level, or real-world generalization claim is made.
