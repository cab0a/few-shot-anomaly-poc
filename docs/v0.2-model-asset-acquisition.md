## English Summary

This record acquires the fixed DINOv2 source revision and standard `dinov2_vits14` checkpoint into an ignored external cache, records their transport and observed identities, and validates their archive and pickle containers without executing source or deserializing the checkpoint. Both assets pass this narrow acquisition boundary. The result permits a separate weights-only and strict-architecture-load verification; it is not model-execution, latency, or anomaly-performance evidence.

## Transport Controls

The acquisition process:

1. required a clean, committed implementation identity;
2. issued HTTP `HEAD` before each transfer;
3. required HTTPS and an asset-specific host allowlist;
4. allowed the source redirect only from `github.com` to `codeload.github.com`;
5. required the checkpoint host to remain `dl.fbaipublicfiles.com`;
6. streamed each response into a uniquely named `.part` file;
7. calculated SHA-256 and byte count during transfer;
8. required the checkpoint to remain exactly 88,283,115 bytes;
9. inspected each temporary artifact before acceptance; and
10. atomically renamed only accepted artifacts to hash-addressed filenames.

Any failure removed the partial and unaccepted assets. The final source response supplied 2,869,642 bytes and the same codeload ETag previously recorded. The final checkpoint response supplied:

| HTTP field | Value |
| --- | --- |
| Status | `200` |
| Content-Type | `binary/octet-stream` |
| Content-Length | `88,283,115` |
| ETag | `"0bd1417efc23bdb1d69200156f5a22bc-11"` |
| Last-Modified | `Thu, 13 Apr 2023 22:01:20 GMT` |
| Range support | `bytes` |

The multipart-style ETag is retained as opaque HTTP metadata. It is not treated as MD5 or SHA-256.

## Checkpoint Container Inspection

The checkpoint passed non-deserializing inspection:

| Check | Result |
| --- | --- |
| Format | PyTorch ZIP |
| Top-level directory | `vits14_pretrain` |
| Members | 177 files |
| Tensor-storage members | 175 |
| ZIP CRC | pass for every member |
| `data.pkl` protocol | 2 |
| Pickle opcodes | 7,128 parsed without execution |
| Candidate state-key markers | 175 |
| Candidate-key manifest SHA-256 | `21dec8566e545b724414a5881a72aa9590525cb81b8b38d416d21e7952eff0f1` |
| `version` member | present |
| `byteorder` member | absent; recorded, not silently inferred |
| Unsafe path, duplicate, encryption, or special type | none |

The pickle global references were restricted to:

- `collections OrderedDict`;
- `torch FloatStorage`;
- `torch Tensor`;
- `torch._tensor _rebuild_from_type_v2`; and
- `torch._utils _rebuild_tensor_v2`.

An arbitrary-global fixture such as `os.system` is rejected by unit tests. Parsing pickle opcodes does not deserialize the checkpoint, reconstruct storage, create a tensor, or inspect tensor values. Consequently, the 175 candidate state-key markers are structural evidence only. Exact key count, tensor shape, dtype, element count, finite-value status, and architecture compatibility remain pending.

The absent `byteorder` member is consistent with an older PyTorch ZIP serialization shape. It is explicitly retained as a compatibility question for the controlled weights-only load rather than being silently treated as a pass for executable use.

## Stopped Development Attempts

Four development attempts stopped before the final accepted run:

1. a commit-identity validator incorrectly expected a 64-character SHA-256 instead of a 40-character Git commit; validation stopped before network transfer;
2. the source check expected a literal complete checkpoint filename, while the fixed upstream loader constructs it dynamically; the downloaded source partial was removed;
3. the checkpoint check required the newer optional `byteorder` member; the 2023 checkpoint lacks it, so both unaccepted assets were removed; and
4. the pickle allowlist omitted two observed standard PyTorch reconstruction references; arbitrary globals remained forbidden, and both unaccepted assets were removed.

After correcting and testing those factual assumptions, the acquisition implementation was committed and pushed. The formal acquisition was then repeated from clean commit `64a1634056ce452a4080848f9a4cc0177f4d0a69`. It produced the accepted hashes above. No failed partial or superseded accepted asset remains.

These stops changed validation fidelity, not the preregistered model, source revision, checkpoint URL, dependency set, evaluation gate, or future workload.

- cryptographic hashing;
- tar and ZIP metadata inspection;
- decompression for member hashing and CRC verification; and
- pickle opcode parsing without unpickling.

- source extraction or import;
- checkpoint deserialization or pickle execution;
- tensor reconstruction or value inspection;
- DINOv2 model construction;
- strict state-dictionary loading;
- model inference or feature extraction;

## Verification

The committed tests fix the provenance identity and the non-execution boundary:

```bash
uv run --locked --no-sync ruff check .
uv run --locked --no-sync pytest
```

A fresh acquisition requires network access and an empty ignored destination:

```bash
reproduction_root="data/external/v0.2/model-assets-reproduction"

uv run --locked --no-sync python scripts/acquire_v0_2_model_assets.py \
  --artifact-dir "${reproduction_root}" \
  --output /tmp/v0.2-model-asset-acquisition.json \
  --project-root . \
  --acquisition-date 2026-07-31 \
  --acquisition-base-commit "$(git rev-parse HEAD)" \
  --preregistration-commit e9330be10742947e4227ced4c99acafe4d098566
```

Because upstream does not publish independent digests, a new acquisition must compare its observed source and checkpoint SHA-256 values with this record. Changed bytes are a stop condition and must not overwrite or silently replace the accepted assets. HTTP metadata can change independently and therefore the complete JSON is not claimed to reproduce byte for byte across dates.

## Decision

### Result: `PROCEED TO WEIGHTS-ONLY STRICT LOAD VERIFICATION`

The current acquisition gates pass:

1. fixed source revision and standard model identity remain available;
2. standard source and weight license evidence is reviewable;
3. final acquisition ran from a committed implementation;
4. both transfers remained within the fixed HTTPS host boundary;
5. checkpoint byte count matched the preregistration;
6. both observed SHA-256 identities were recorded;
7. both containers passed non-executing structural checks; and
8. third-party assets remain outside Git and separate from PolyForm.

This decision does not accept the checkpoint for inference and does not adopt DINOv2. The checkpoint still must pass controlled weights-only CPU deserialization, finite-value checks, exact tensor inventory, model construction from the fixed local source, and strict state-dictionary loading.

## Next Milestone

The next milestone is **v0.2 weights-only checkpoint and strict architecture load verification**. It must:

1. verify both external asset hashes against the committed acquisition record;
2. safely extract the fixed source to a new ignored hash-addressed directory;
3. import only that local source in the isolated CPU environment;
4. deserialize the checkpoint using the pinned PyTorch weights-only CPU path;
5. reject unsupported root objects, non-string or duplicate keys, non-CPU tensors, non-float32 tensors, non-finite values, or an unexpected tensor inventory;
6. construct non-register `dinov2_vits14` without pretrained network access;
7. require an exact strict state-dictionary load; and
8. commit a machine-readable compatibility record before any inference or benchmark.

It must not access VisA, generate the synthetic timing workload, run model inference, tune the candidate, measure latency, or claim anomaly performance.
