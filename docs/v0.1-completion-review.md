# v0.1 Completion Review

## Status

v0.1 is complete. The public project decision is `REJECT`.

Both shortlisted methods were taken through the fixed sequence from
requirements and research to prototype, evaluation, failure selection, and
decision. Neither method passed every preregistered hard gate. The negative
result remains part of the public evidence.

This review was performed after the public evaluation report commit
`deaf51ce292d2b5ab7c0a560dafcc0488e9e3a75`, which passed
[GitHub Actions CI #31](https://github.com/cab0a/few-shot-anomaly-poc/actions/runs/30441441871).
The completion-review commit must pass the same locked CI workflow before v0.1
is handed off.

## Reproducibility review

### Clone-only verification

The committed source, configuration, lock, synthetic evidence, freeze
identities, and final numerical artifacts can be verified without downloading
VisA:

```bash
uv sync --locked
uv run --locked --no-sync python scripts/verify_environment.py
uv run --locked --no-sync ruff check .
uv run --locked --no-sync pytest
```

The test suite checks:

- deterministic method primitives and failure contracts
- exact frozen-file identities
- byte-reproducible synthetic artifacts
- exact committed calibration and first-scoring summaries
- final artifact manifest and per-file SHA-256 values
- exact final metrics, failure counts, hard-gate order, and decisions
- reuse of the preserved label-free scores, classifications, and latency
- absence of raw images from the final evaluation bundle

### Data-backed reproduction

A complete image-level rerun additionally requires the official
`VisA_20220922.tar` archive, the pinned official split revision, and enough
local storage for extracted data and ignored fitted state. The archive,
extracted images, manifests containing final-test paths, and pickle state are
intentionally not committed.

The recorded run stages and their CI-passed source commits are:

| Stage | Source commit |
| --- | --- |
| Pre-evaluation freeze | `fd9857acb29903fadb570680ecb5d4d8ebf5a5aa` |
| Normal fitting and calibration | `4fef91c1d1e339aa507cad80d51127e01046ae0b` |
| First fixed final-test scoring | `5b142f31c974334545ca2bb63bb7b2c6c514828a` |
| Final label reveal and decision | `c6b4e5e164cc8788ff0428361406ada3e116543b` |

Each recorded runner requires a clean checkout at its declared source commit
and refuses to overwrite an existing output. Reproduction should therefore use
a separate clean worktree and preserve the ignored, hash-checked local state
between the stages. Detailed commands and inputs are in the
[acquisition record](data-acquisition-record.md),
[calibration record](normal-only-calibration.md),
[scoring record](first-fixed-final-test-scoring.md), and
[final evaluation record](final-evaluation-and-decision.md).

The committed metrics and decision can be reconstructed exactly from the
preserved scoring evidence. A second complete raw-image scoring run was not
performed during this completion review. Raw-to-score repeatability is
therefore supported by pinned inputs, software, configuration, and deterministic
contracts rather than an independent repeat experiment. CPU timings are
hardware- and environment-specific; the project does not claim byte-identical
latency on a different machine.

## Public-claim review

The README first screen reports the `REJECT` result and representative metrics.
The detailed report:

- distinguishes ranking metrics from operating-point gates
- states that the requirements are hypothetical
- retains unfavorable false-positive, false-negative, recall, and latency
  evidence
- avoids a production or state-of-the-art claim
- limits the result to VisA `pcb1`, one split, one seed, and one reference set
- does not generalize benchmark or synthetic evidence to real inspection

The scorer did not receive a class field or branch on class. However, VisA
relative paths contain class-semantic directory names. This is recorded as a
limitation: v0.1 has a programmatic label-use boundary, not a double-blind human
protocol. A future evaluation should use opaque asset IDs.

## Deferred scope

The following remain deferred rather than silently added to v0.1:

- DINOv2 patch nearest neighbor
- AnomalyDINO and PatchCore
- pixel-level localization or segmentation evaluation
- image-content failure review and public failure figures
- GPU benchmarking
- additional VisA categories or reference-set sweeps
- Web UI, API, Docker, database, and cloud deployment

Any v0.2 study requires a new preregistration and untouched evaluation
boundary. The first proposed question remains whether a pinned DINOv2
patch-nearest-neighbor method improves fixed-threshold recall enough to justify
its CPU, model-asset, and dependency cost.

## Handoff

v0.1 is a completed negative PoC, not an adopted inspection method. The next
technical step is not deployment. It is a separately scoped validation of the
selected failure images and operating-point transfer, followed only if
justified by a preregistered v0.2 representation comparison.
