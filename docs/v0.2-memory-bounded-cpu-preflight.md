## English Summary

This document preregisters a second DINOv2 CPU preflight before any timing result exists. It preserves the first stopped attempt and keeps the same CPU, model, scoring path, resolutions, input bytes, invocation counts, latency gate, and reproducibility rule. It corrects two resource-handling defects: total visible RAM becomes diagnostic rather than gating, and deterministic synthetic images move from simultaneous in-memory retention to local memory-mapped storage with one-image-at-a-time loading. Actual out-of-memory events, process termination, missing observations, and incomplete runs remain hard failures.

## Why a New Preflight Is Required

Attempt 1 compared:

```python
os.sysconf("SC_PHYS_PAGES") * os.sysconf("SC_PAGE_SIZE")
```

with an exact previously observed lower bound. `SC_PHYS_PAGES` is the number of physical pages exposed by the running kernel, and `SC_PAGE_SIZE` is the byte size of one page. Their product describes total RAM visible to WSL; it does not describe current workload usage, free memory, or process resident memory.

The attempt observed `4,045,004,800` bytes against `4,045,017,088` bytes, a difference of `12,288` bytes or three 4,096-byte pages. No model was constructed and no invocation ran. The stop therefore provides no evidence of an out-of-memory condition or DINOv2 resource use.

The original project requirements treat peak memory as non-gating diagnostic evidence. An exact total-RAM snapshot gate did not test that requirement and could reject the same constrained environment before its workload was observed. The result is retained as a protocol-design failure, not converted into a model-performance result.

## Exactly Two Protocol Changes

### 1. Total RAM becomes diagnostic

The runner must record, when available:

- total visible RAM from `SC_PHYS_PAGES * SC_PAGE_SIZE`;
- `MemTotal`, `MemAvailable`, `SwapTotal`, and `SwapFree` from `/proc/meminfo`;
- process peak resident set size from Linux `resource.getrusage`;
- whether the kernel or process reported an out-of-memory condition; and
- process exit status and observation completeness.

The prior `4,045,017,088`-byte value remains in the record as historical comparison only. Falling below it is not a stop condition. Failure to obtain one optional RAM diagnostic must be recorded as unavailable and must not be represented as an out-of-memory failure.

Memory is a hard failure only when the fixed workload cannot complete: a Python `MemoryError`, framework out-of-memory exception, operating-system termination, nonzero resolution-process exit, missing observation, non-finite score, or incomplete set of 300 timed invocations fails that resolution. If both resolutions fail, the preflight returns `DO NOT PROCEED`.

Peak RSS has no acceptance threshold in this preflight. It is a diagnostic needed to explain feasibility on the recorded machine and to inform a later implementation budget without changing the one-second latency gate.

### 2. Synthetic images use bounded resident storage

The exact synthetic byte stream remains fixed:

| Item | Fixed value |
| --- | --- |
| Generator | `numpy.random.Generator(numpy.random.PCG64(42))` |
| Generation order | 20 reference arrays, then 100 query arrays |
| Array shape | `512 x 512 x 3` |
| Array dtype | `uint8` |
| Values | integers in `[0, 256)` |
| Reference IDs | `synthetic/reference/000` through `synthetic/reference/019` |
| Query IDs | `synthetic/query/000` through `synthetic/query/099` |

Before model timing begins, the runner must generate those 120 arrays in the fixed order into a new local memory-mapped file outside Git. It must hash the contiguous bytes of each array and record the 120 SHA-256 values. The file path itself must not enter a public artifact; only a relative logical input-store identity, byte count, shape, dtype, and hashes may be recorded.

Reference memory construction must load one reference image into one contiguous in-memory `uint8` array, extract its features, append only the normalized patch features required by the memory bank, and release the source-image array before loading the next reference.

Warm-up and timed scoring must load or copy exactly one query image into one contiguous in-memory `uint8` array before the timer starts. File access and the memory-map-to-array copy remain outside the existing timed boundary. The timer still begins immediately before decoded-RGB-array conversion and ends after materialization of one finite scalar score. Query order, repetition, and score identities remain unchanged.

The 20-image feature memory bank, fixed model, current query array, and necessary scoring intermediates may remain resident. Batch scoring and simultaneous retention of all source images are forbidden.

## Unchanged Contract

All other clauses of [`v0.2-dinov2-cpu-preflight-1`](v0.2-preflight-preregistration.md) remain controlling by exact reference. In particular, this preflight does not change:

- the standard non-register `dinov2_vits14` source revision or checkpoint;
- CPU-only float32 inference, deterministic algorithms, or isolated dependencies;
- exact blocked cosine nearest-neighbor scoring and top-one-percent aggregation;
- the 20-reference budget or 100-query workload;
- resolutions `224` and `448`, run in that order in fresh processes;
- 4 PyTorch intra-op threads, 1 inter-op thread, or environment thread controls;
- batch size 1, default CPU affinity, default priority, or AC-power requirement;
- 25 untimed warm-up calls per resolution;
- three ordered passes over 100 query IDs, producing 300 timed invocations per resolution;
- `time.perf_counter_ns`, median, or nearest-rank p95 calculation;
- the `p95 <= 1.0 s/image` gate;
- the prohibition on retries, discarded observations, and outlier removal;
- the offline first-10-score tolerance of `1e-6`;
- the resolution selection table;
- the ordered stop conditions other than the total-RAM interpretation inside condition 6;
- the untouched VisA `pcb2` boundary; or
- the prohibition on anomaly labels, threshold calibration, and anomaly-performance claims during preflight.

No result from attempt 1 motivated a model, resolution, thread, workload-count, latency-gate, or score-tolerance change because attempt 1 produced no timing or scoring result.

## Memory and Failure Evidence

Each fresh resolution process must write enough evidence to distinguish:

- successful completion with finite scores;
- a caught Python or framework memory exception;
- a caught non-memory scoring exception;
- a nonzero child-process exit;
- operating-system termination or absent child output;
- an incomplete observation count;
- non-finite scores; and
- a completed run with recorded peak RSS.

The parent runner must retain a failed resolution record and continue to the second resolution when the process remains controllable. It must not retry an invocation or change model settings after a failure. A failure in one resolution does not waive the fixed evaluation of the other resolution.

## Ordered Stop Conditions

Conditions retain the order defined by the superseded preregistration:

1. preregistration identity;
2. source and license;
3. dependency resolution;
4. checkpoint acquisition;
5. third-party separation;
6. revised target-machine identity;
7. execution integrity;
8. CPU latency and completion result;
9. offline score reproducibility; and
10. untouched evaluation boundary.

The preflight stops before timing if conditions 1 through 7 fail. Condition 8 returns `DO NOT PROCEED` if neither resolution completes and passes the fixed latency gate. Later success cannot waive an earlier failure.

## Decision Rule

Return `PROCEED` only when:

- conditions 1 through 7 pass;
- at least one resolution completes all 300 observations with finite scores and p95 no greater than one second;
- the offline reproduction check passes for every passing resolution; and
- the untouched evaluation boundary remains feasible.

Otherwise return `DO NOT PROCEED`. Peak RSS, total RAM, available RAM, median latency, and a favorable synthetic score cannot override a failed hard condition.
