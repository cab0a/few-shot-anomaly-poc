## Question Answered

This checkpoint answered one remaining preflight question: can the future `pcb2` final-test boundary be created so that a scorer receives only opaque file identities while source paths and labels remain outside its input?

It did not prepare that real boundary. The check exercised the same separation rules with three synthetic byte files in temporary ignored storage and discarded them after verification.

## Implemented Boundary Contract

The new primitive fixes these controls before real boundary preparation:

1. Validate canonical relative source paths, unique records, regular files, and retained extensions.
2. Sort source records deterministically by `HMAC-SHA-256(secret_key, source_path)`.
3. Assign sequential IDs from `asset-000000` without carrying semantic source names forward.
4. Copy bytes to `assets/<opaque-id>.<extension>` and verify byte count and SHA-256 after copying.
5. Limit every scorer record to `asset_id`, `relative_path`, `byte_count`, and `sha256`.
6. Write `asset_id`, source path, and class label only to a separate sealed mapping outside the scorer root.
7. Refuse existing output roots or manifests instead of overwriting them.
8. Keep the ordering key out of both manifests and every published report.

The scoring-manifest loader rejects any additional field, including a source path, class label, split value, or HMAC key.

## Known Limitations

- Synthetic files demonstrate programmatic feasibility, not the availability or content of real `pcb2` records.
- Separate filesystem locations and a strict scorer API are implemented; process-level permissions and operator procedure must be fixed and verified during real boundary preparation.
- HMAC ordering hides semantic order from the scorer but is not encryption of public source identities.
- No claim is made that public VisA labels are unknowable; the boundary is procedural and auditable.
- No anomaly performance, threshold stability, cross-category transfer, production behavior, or real-world generalization was measured.
